1. Objectives and scope

SmartClass helps a UM lecturer run a class: students sign in with their SPeCTRUM (Moodle) account, a camera at the door records attendance by face recognition, attendance is copied to SPeCTRUM, and an AI assistant answers questions from the lecturer's own course materials with citations. Since AP1, IoT environment control and desk projection were dropped from the scope (proposal revision, November 2026).

3. System design

All diagrams are in one Lucidchart document, generated from the code (the ERD from the SQLAlchemy models that the Alembic migrations build): SmartClass - Design Diagrams (AP2). PNG exports are in docs/diagrams/.

3.1 System architecture

Two React Native (Expo) apps (student, lecturer; the lecturer app also runs in a browser and holds the admin area) call a FastAPI backend. The backend uses PostgreSQL with pgvector, a local Moodle 4.5 that simulates SPeCTRUM, an LLM provider through one adapter, and InsightFace for face recognition. A camera device client (Raspberry Pi or laptop webcam) sends face crops to the backend.

4. Methodology and development

4.1 Methodology

Incremental development in small tasks. Each task in PLAN.md cites the requirements it covers and a "Done when" line. A task is finished only when its code and tests are written, the fast checks pass (lint, backend tests, app unit tests), a separate reviewer checks the change for bugs and weakened tests, and, for screens, its end-to-end flow passes. Human checkpoints after each module (T23, T48, T94) are where I test on a real phone and in a browser before more is built. Progress and decisions are logged in PROGRESS.md.

4.3 What was built per module

Module 1. Students and lecturers sign in with their Moodle account; the account and role are created on first login, and courses and enrolments sync from Moodle every 15 minutes. Students give PDPA consent, take three guided selfies and a photo of their matric card; the server compares the faces and reads the matric number. A clear pass is approved at once; anything else goes to the lecturer's verification queue. Administrators manage accounts, devices, Moodle sync and the audit log in the browser.

[Screenshot: student face enrolment status screen (no real face or card visible)]

[Screenshot: lecturer web, admin Accounts page with test accounts]

Module 3. Sessions open 15 minutes before each scheduled class and close at its end. Statuses are Present, Late, Excused and Absent; the lecturer can override any status, start a class now, extend it or end it early. Closed sessions are copied to the Moodle Attendance activity and retried when Moodle is down. Students see their rate and history per course.

[Screenshot: lecturer live session with counts and sync status]

[Screenshot: student attendance rate and history]

Module 4. The device client detects faces locally and sends crops with its device key. The server matches them against the enrolled students of the open session and records attendance after 3 matching frames. The student gets an "attendance recorded" banner; a student who was missed can flag it, and the lecturer confirms or rejects with the closest unmatched face as evidence.

[Screenshot: student "I'm here" flag and the lecturer's flag alert]

Module 8. Course materials are read from Moodle, split into passages with file and page, and embedded. Students chat with a cited assistant per course, open a cited PDF at the page, and make summaries, flashcards and practice questions. Lecturers see sync status per material, anonymous question trends, a "before next class" summary, and can ask their own materials.

8. Limitations and next steps

  • Sign-in uses the simulated SPeCTRUM's username and password; real SPeCTRUM uses Microsoft 365 SSO and would need UM IT approval.
  • No liveness detection (proposal §4.9); the camera is at the entrance under the lecturer's watch.
  • To do before the final demo: Raspberry Pi run with fps and latency measured (T47), full class run end to end (T48), Q&A evaluation set (T83), UAT server and APKs (T99), small UAT (T107).
